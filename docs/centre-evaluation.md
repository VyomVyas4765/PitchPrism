# Centre evaluation integration

The Dev 2 evaluation entry point consumes **redacted, extracted evidence**, not a raw PDF. Dev 1's upload/extraction stage must store the immutable original privately, then produce the `CentreExtractedInput` contract in `packages/contracts/schemas/centre-extracted-input.json`. The submission must already belong to a centre. The planned business site in `context.plannedBusinessLocation` is authoritative when phone GPS or the applicant's home differs.

Each answer has one of `answered`, `missing`, `not_asked`, `irrelevant`, or `unreadable` and cites segment IDs. Profile skills/experience may be represented as `profile` segments and cited fields. A profile-confirmed business site must cite its own profile segment; it replaces a conflicting PDF location for scoring and is flagged for assessor review. PDF segments carry page and, when available, bounding box, original-language text, English translation, read confidence, and struck/superseded state. The extractor redacts name, phone, email, exact address, and social category before this handoff. The API and worker reject detected phone/email patterns and invalid citations; this is defense in depth, not a substitute for Dev 1's redaction and private original storage.

Centre assessor and cohort lead sessions may submit an extracted input to `POST /api/v1/centre/submissions/:id/assessment`. The route checks centre scope and active processing consent, uses the server's provisional rubric and local Python scorer, stores two model runs and citations, and archives any earlier undecided evaluation. The user-requested Groq path is `POST /submissions/:id/evaluate-pdf`: it reads the private original after the same scope and consent checks, maps and redacts either supported English digital business idea form family locally, then invokes Groq only for domain judgements. The Python worker computes all totals in code, and the API refuses a decided-case rescore. `GET /api/v1/centre/queue` and `/submissions/:id/card` serve the one-view web review screen. `POST /submissions/:id/decision` records Shortlist, Not yet, or More information; override reasons are required when the assessor departs from the suggested pathway or shortlists a low-information idea. `PUT /submissions/:id/feedback` saves an English draft with `awaiting_translation_and_delivery` status. The applicant-facing submission status reflects the human decision.

With no approved `LOCAL_LLM_MODEL`, the legacy extracted-input CLI returns `pending_model` and no potential score. The installed `llama3.2:latest` completed one synthetic format run, but gave a very high score to generic synthetic text; it is **not approved for production scoring**. The PDF path uses the user-requested Groq exception (D-31). A missing/rejected key or schema failure never creates a scored card. Both API paths invoke a Python CLI synchronously as an integration bridge; production queue scheduling, rubric administration, cost telemetry and full PDF coverage remain pending. For English centre imports, `POST /submissions/:id/processing-consent` stores an immutable, locally decoded audio recording of the applicant's agreement and uses Dev 1's append-only consent service. The assessor must attest to reading the current notice; the server verifies a playable audio duration, not the spoken words. No consent is inferred from upload or a click alone.

The development/test evaluator desk has a separate unsaved `POST /evaluate-preview` multipart path for judge demos. It accepts the supported English digital two-page business idea form families, uses the same local extraction/redaction and Groq scorer, returns the scorecard directly, and does not write a Submission, original, consent or CentreCase. It is centre-staff-only, allows one running preview per account, and is disabled in production. The browser keeps the original PDF in a temporary object URL for side-by-side review. This demo path does not establish applicant consent; the production record workflow above remains consent-gated.

Preview failures are now separated at the Python/Node boundary: an unsupported layout or unreadable answer, invalid/redaction-failed evidence, and a temporarily unavailable worker have distinct safe HTTP messages. The worker does not return raw PDF text, stack traces, provider responses or credentials in those errors. The known EDP Scenario 1 sample passed an authenticated upload through the live dashboard proxy on 2026-10-18 (HTTP 200, 83 potential in that pass). Other EDP scenarios still need validated extraction, including missing and overwritten answers.

After a repeated user report, the preview now returns an allowlisted extraction reason (page layout, header name, printed question alignment, unreadable answer, or privacy redaction failure) and the browser error includes the selected filename and byte count. This information does not contain applicant answers. The repository's English Scenario 1 copy is 15,327 bytes and passed another authenticated browser-proxy upload; the English Scenario 2 copy produced the expected `answer_unreadable` error. A browser-selected file that still fails can now be compared without collecting the private PDF or logging its text.

That diagnostic identified the user's actual upload as a separate 29,990-byte English Business Idea form-fillup. The form-fillup family parser now reads printed question anchors and right-column answer regions rather than fixed row heights. It uses the `Name` header for local redaction, omits the customer age/gender boxes from scoring, withholds the full location answer, drops any non-location sentence containing a possible exact address, and cites the actual price/revenue anchors in the unverified-financial flag. Blank answer boxes are `missing`; omitted questions are `not_asked`. The original EDP mapping remains unchanged. All six local English form-fillup examples passed extraction/schema/redaction checks. Example 5 passed local and authenticated dashboard-proxy scoring on 2026-10-18 (63 and 58 provisional potential; 100 completeness, 90 domain coverage). No general form/OCR support is implied.

Readiness is scored only when the extracted input cites relevant skills or experience. For the English Business Idea form-fillups, an explicit affirmative answer to "Do you have an existing business?" becomes a cited `experience` segment; "No", an omitted question or an empty answer does not imply low readiness. The six local form-fillup examples contain no affirmative existing-business answer, so their Readiness row correctly says **Not assessed** rather than inventing a score. The card explains the gap and asks what relevant training, experience or completed action the applicant can confirm. This follow-up is not yet a write-back/rescore flow.

The screen pairs each domain score and reason with the actual redacted answer segments cited by that PDF's assessment. Each segment shows its source page, and the original viewer can open that page. Source IDs and text come from the current upload or stored case, never a fixture. The extractor also retains bounding boxes, but highlighting the precise source region still needs the shared evidence viewer. Dev 1 also owns general PDF extraction, mobile upload, translation/TTS, entrepreneur follow-up answers, and feedback delivery. Dev 3 owns published rubric versions, cohorts, trade administration, and the queue. Dev 2 still must connect local-market sources, similarity/duplicates, rankings, imports, route suggestions, cohort views, and remaining P1 tools; none is represented as complete by this slice.

## Multi-entrepreneur comparison workspace · 2026-10-18

The centre landing screen now compares all its saved submissions. `GET /api/v1/centre/portfolio` supplies the generated `CentrePortfolio` read contract: scoped paginated rows; cohort/trade/language/lane/search/sort filters; a selected rubric version; full-filtered-population chart data; trade/cohort ranks; domain medians and interquartile ranges; score distributions, pathways and a trade × cohort heatmap. Pagination never changes aggregate counts. Ranks use the full same-version centre population rather than search results. Missing scores, missing rubric versions, unassessable cases and coverage below 60% are unranked. Ties use competition ranks. A trade/cohort with fewer than five rankable ideas falls back to its centre trade; below five peers the rank and sample size remain visible but no percentile is given. Wider HQ benchmarks, investment norms and materialized worker rank refresh remain pending. A 5,000-submission comparison limit fails explicitly instead of returning misleading partial aggregates.

Assessor and cohort-lead sessions can select two to four scored ideas for side-by-side domains, source quotes, customer/offering/funding/revenue claims, follow-up questions and pathways. Original/evidence review and human decisions remain on the existing drawer. The decision stores a rank snapshot, while the table keeps showing live ranks. `GET /intake-options` returns centre-owned cohorts and active trades; optional `cohortId` and `tradeKey` on `/plans` are validated on the server. Existing unclassified imports remain visible and unranked by trade until classification exists. No automatic trade inference was introduced.

The explicit local demo loader (`backend/src/modules/centre/seed-demo.ts --local`) creates a separate reserved centre, account, two cohorts, three trades, 18 synthetic entrepreneurs and synthetic two-page originals with illustrative scores and evidence. The synthetic workspace and review drawer disclose fixture provenance. Scores use the provisional EDP weights; no model quality claim or real-person consent is seeded. Untouched fixtures can be refreshed explicitly; human decisions are preserved. HQ reports exclude this reserved centre. Real accounts cannot see its individual ideas. The previous unsaved PDF preview remains separate and never enters portfolio rankings.

The scorer's undefined `prompt_for` call is repaired. Each chunk now receives only its requested domains, cited evidence and criteria; the 1–5 evidence anchors are explicit, under prompt version `edp-score-v2`. Two-run disagreement, missing-domain and PII guards remain tested. This improves the specification and restores execution; it does not establish organiser-data accuracy. Multilingual/OCR validation, semantic similarity, local-market sources, exports and the rest of the earlier duty brief remain pending.


## Browser batch evaluation · 2026-10-18

The evaluator now has separate saved/demo-portfolio and batch-preview tabs. Batch accepts up to 30 selected/dropped PDFs (12 MB/file, 120 MB total), snapshots queued files on Evaluate, and calls the same authenticated non-production `/evaluate-preview` endpoint sequentially. Results enter the shared comparison view as they complete; original object URLs and cards stay browser-local. Errors are isolated per file, retry returns failed files to the queue, and pause finishes the current request without launching the next. Switching tabs preserves the batch; reload/unmount clears it. No Submission, consent, ImportBatch or decision is created by this preview. Saved production bulk import and ZIP remain pending.

Server and browser now import the same pure `buildPortfolio` implementation from contracts; access scope is still established only by the server. Trade/cohort labels on unsaved files are explicit evaluator labels, not inferred classifications. The browser can inspect source evidence and originals but cannot save a human decision for unsaved previews.

A live two-PDF synthetic smoke test reached a provider `json_validate_failed` error on an oversized evidence array. The centre adapter now uses three named nullable citation slots on the wire, validates that wire response, then validates the mapped public 1–3 citation array and existing evidence IDs. Extra/missing/duplicate slots are rejected; provider failed-generation text is never salvaged or logged. Real synthetic scoring and browser comparison passed after the change. Provider context: [Groq structured-output documentation](https://console.groq.com/docs/structured-outputs). No model/provider or broader hosted permission was added.
